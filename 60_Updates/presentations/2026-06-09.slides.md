## Training now writes durable, resumable I/O

### T1, infrastructure (the unlock for logged runs)

- **Checkpoints**: step-cadence (rotated to `keep_last`) plus never-rotated `best.pt` / `final.pt`. Only trainable adapter/encoder weights + optimizer state are stored; the frozen base is rebuilt from its own ckpt (`strict=False`).
- **Periodic eval cycle**: `evaluate()` averages held-out loss in `eval()`/`no_grad`; `best.pt` tracks improvement.
- Selection defaults to **`base_loss`, not the total**, because self-distilled shortcut terms can collapse to ~0 without real improvement, so they must not drive checkpoint selection.

> All opt-in via `training.output_dir`; runs without it are bit-identical to before. Verified: **135/135 tests pass** (CPU), plus a dummy-backbone smoke run produced correct checkpoint rotation, best-tracking, and load roundtrip.

## What `anchor_prob` is doing

### D3, the shortcut training knob

Each training sample draws `b ~ Bernoulli(p)` with `p = anchor_prob`:

```
L  =  b · L_anchor                 # standard flow/diffusion loss at the finest step d_min
   +  (1 - b) · L_self_consistency

L_self_consistency:  s(x_t, t, 2d)  =  ½ s(x_t, t, d)  +  ½ s(x_{t+d}, t+d, d)
```

- **Why we need it.** The anchor grounds the prediction in real data so the self-consistency target cannot collapse (to `s = 0`, or to a constant field independent of `d`). It pins the bottom rung; consistency then bootstraps the larger steps off it.
- **Why we will play with it.** `p` trades data-grounding against few-step consistency: `p = 1` is pure diffusion (no shortcut, the ghosted clip), while too-low `p` weakens grounding and risks collapse. `0.5` worked here; the paper uses `0.75`. We will sweep it.

## Correction: actions are wired, but not effective

### D4, reframing the action task

- Earlier we assumed the shortcut adapter was *step-level only*. That was wrong: the AVID config already declares the `act` condition, the adapter UNet is natively `action_conditioned: True`, and `a_t` reaches its action head.
- Yet predicted dynamics still look **somewhat random / not action-following** locally. So this is a *diagnose-why* task, not an *add-wiring* task.

::: columns
**Leading suspects**

- **Frame stride too small**: consecutive frames barely move, so the per-frame delta action is too fine-grained to displace the prediction (its own open decision).
- **Undertraining**: small data + small batch (local); the sharp `0.5` figure came from this same action-wired config.
|||
**To rule out**

Actions null/dropped at train or eval; `a_t` not held fixed across the self-consistency micro-step (would make the target ill-defined).
:::
